# Phase 1 follow-up items (not blocking)

Items surfaced during Phase 1 execution that don't block the canonical
operators layer from landing but should be fixed before Phase 2 or as
dedicated follow-up commits.

---

## faa-operators-full.ts ingests aircraft owners as operators

**Discovered**: 2026-04-18, during commit 6 (FAA → canonical backfill) dry-run.

**Finding**: `faa_operators` contains 3,898 rows, but only **50 are real Part 135 operators**:
- 48 with synthetic cert codes matching `^[A-Z]{4}[0-9]{3}$` (NETJ001, FLEX001, WHEE001 — generated by `faa-operators-full.ts` from the ICAO_OPERATOR_MAP).
- 2 with real FAA Part 135 cert format matching `^[0-9][A-Z]{3}[0-9]{3}[A-Z]$` (`1OCA082A` Priester Aviation, `7OCA297N` Jet Linx Aviation).

The remaining **3,848 rows have `certificate_number = name`** — legal entity names (LLCs, trusts, individual owners) that `faa-operators-full.ts` pulled from `faa_aircraft.certificate_holder` without a proper operator filter. Examples: `YATES AVIATION LLC`, `CHERRY ROAD LEASING LLC`, `BUILDING PRODUCTS INVESTMENTS INC`. These are aircraft owners, not operators.

**Impact in Phase 1**: the commit 6 backfill filters to the 50 real rows and leaves the 3,848 out of the `operators` canonical layer. The rest belong in the Phase 3 aircraft canonical layer (as `aircraft.owner_name` → separate `owner_identities` entity, if needed).

**One known leakage** in the 50: `TVPX001 TVPX ARS` — a trust company that was in `EXCLUDE_PATTERNS` in `faa-operators-full.ts` but still ended up with a synthetic cert code. Low-priority to manually clean.

**Fix**: rewrite `faa-operators-full.ts` so:
1. The operator list is built from a curated ICAO-operator map + verified Part 135 certs only, not by promoting `certificate_holder` values wholesale.
2. Trust/bank/individual-owner EXCLUDE_PATTERNS are applied at the cert-generation step, not after.
3. Aircraft-owner records land in a dedicated `aircraft_owners` table (or stay as `faa_aircraft.certificate_holder` without being duplicated into `faa_operators`).

**Priority**: pre-Phase-2. Blocks cleanly expanding the operator canonical layer when new sources land. No data migration required — commit 6 only backfilled the 50 good rows, so re-running after a source fix is additive.

**Tracking**: this document (this section). No Linear/GitHub issue yet.

## Synthetic cert numbers are not authoritative FAA IDs

**Context**: the 48 synthetic codes (NETJ001 etc.) were generated from the `ICAO_OPERATOR_MAP` inside `faa-operators-full.ts`. They're stable internal IDs but not real FAA Part 135 certificates.

**Impact**: `operator_identities.source_id` for these rows stores the synthetic code. Any attempt to cross-reference against a real external FAA cert ID will fail.

**Mitigation (already applied in Phase 1)**: commit 7's safety_ratings matcher uses **name-fuzzy matching**, not cert_number JOIN. The original "1 of 313 matched" failure was specifically the bug of assuming cert_numbers aligned across sources — the MDM redesign (canonical + identity + name-fuzzy) is the fix.

**Fix**: when the faa-operators-full.ts rewrite lands (see above), the 2 rows with real FAA cert format (`1OCA082A`, `7OCA297N`) stay. The 48 synthetic rows either (a) get replaced with real cert numbers if we can source them, or (b) stay as-is with the synthetic convention documented.

**Priority**: deferred. Name-matching covers this; real cert IDs are a nice-to-have for deterministic matches against future sources that include them.
